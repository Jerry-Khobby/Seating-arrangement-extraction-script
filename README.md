# OMS Seating Arrangement ETL

## Overview

This project extracts and normalises weekly seating arrangement data from SharePoint CSV exports across three Ghana office locations — **Kumasi**, **Takoradi**, and **Accra**. The data is transformed into clean, structured tables that are ready to be loaded into the Office Management System (OMS) database schema.

The core problem this solves is that each office maintains its seating spreadsheet in a completely different format and layout. This script reads all three, understands their individual structures, and produces a unified set of output tables — including which employees are working remotely on any given day, derived purely from whether their seat was empty or occupied.

---

## Background & Business Context

The company operates across multiple countries (Ghana, Rwanda, Germany, and the US). Within Ghana, there are three offices:

- **Kumasi Office** — a multi-floor building with named rooms (Sekondi, Adiembra, Kweikuma, Apowa, Effiakuma, Apremdo)
- **Takoradi Office** — rooms named after cities (Main Hall, Knit, Mainz, Dortmund, Stuttgart)
- **Accra Office** — organised by block and floor (Block A Floor 0, Block A Floor 1, etc.)

Each week, floor leads and office managers update a SharePoint spreadsheet per office. The spreadsheet tracks which employee is sitting in which seat on each day of the week. When a seat is blank for a day, that employee is understood to be working remotely.

The goal of this ETL is to capture that signal — occupied vs. empty seats — and convert it into a structured remote work log alongside a full occupancy record.

## Input File Formats

Each office's SharePoint export has a different layout. This is the key challenge the script handles. Below is a description of each.

### Kumasi (`Kumasi_Seating_Arrangement_In_office___Remote_.csv`)

**Delimiter:** Comma

**Structure:** The file is divided into sections, one per room. Each section follows this pattern:

```
Row 0:  SEKONDI | 16 | (blank) | FLOOR LEADS | Asumah Yakubu | Samuel Junior Arthur
Row 1:  (blank) | # of unoccupied Seats | Vacant Seat/Day | Seat 1 | Seat 2 | ... | Seat 16
Row 2:  Monday  | 0  | 1  | (blank) | Ayimbila Nsolemna | Kingsley Botchway | ...
Row 3:  Tuesday | (blank) | 1 | (blank) | Ayimbila Nsolemna | ...
...
Row 6:  Friday  | ...
```

- **Row 0** contains the room name (col 0), total seats (col 1), and the floor leads listed after the `FLOOR LEADS` marker.
- **Row 1** is the column header. Note it is shifted one column to the right — seat labels start at column 3, not column 0.
- **Data rows** (Mon–Fri): column 0 is the day, columns 1–2 hold vacancy counts, and columns 3 onwards hold the employee names seated that day. A **blank cell** in a seat column means that seat is empty — the assigned employee is remote.
- Rooms in this file: **Sekondi, Adiembra, Kweikuma, Apowa, Effiakuma, Apremdo**

---

### Takoradi (`New_Seating_Seating_Arrangment_-_Update__________Takoradi.csv`)

**Delimiter:** Comma

**Structure:** Room names appear in **column 1** (column 0 is always blank for header rows). Each room can contain multiple seat-range sub-blocks — for example, a room with 48 seats will have sub-blocks covering Seats 1–24, then Seats 25–48 on separate rows. Each sub-block starts with a `Days` header row listing seat numbers.

```
Row N:    (blank) | MAIN HALL | 0
Row N+1:  Days | Daily Empty Seats | Seat 1 | Seat 2 | ... | Seat 24
Row N+2:  Monday  | 0 | Robert Elinam Hlovor | Maxwell Kwesi Ehiawey | ...
...
Row N+6:  Friday  | ...
Row N+7:  (blank separator)
Row N+8:  Days | Seat 25 | Seat 26 | ...   ← continuation sub-block
Row N+9:  Monday  | 8 | Adolf Menano | ...
```

- The room name is detected by finding a row where column 0 is empty and column 1 contains a non-numeric, non-seat-label value.
- Sub-blocks within a room are detected by scanning for `Days` rows inside the room's range.
- Rooms in this file: **Main Hall, Knit, Mainz, Dortmund, Stuttgart**

---

### Accra (`Arrangements_Final-_Accra.csv`)

**Delimiter:** Semicolon (`;`) — not comma

**Structure:** Rooms are identified by a header row matching the pattern `BLOCK <letter> FLOOR <number>`. Each room block is followed by a `Day` column-header row, then the five day rows.

```
Row N:    BLOCK A FLOOR 1
Row N+1:  Day | Seat 1 | Seat 2 | ... | Seat 9
Row N+2:  Monday  | Jeffery Afutu | Phinehas Anteh | ...
...
Row N+6:  Friday  | ...
```

- Some seats are labelled `Book before Use` — these are hot-desk seats available for booking and are not assigned to any employee. The script flags these as `is_hot_desk = True` and does not treat them as employee names.
- Rooms in this file: **Block A Floor 0, Block A Floor 1, Block A Floor 2, Block B Floor 0, Block B Floor 1, Block B Floor 2**

## How Remote Detection Works

The script does not rely on any explicit "remote" flag in the source data. Instead, it infers remote status from seat occupancy:

1. For each room, the script builds a **roster** — the full set of all employee names that appear in any seat on any day of the week for that room.
2. For each day, it records which employees are **present** (their name appears in a seat column).
3. Any employee in the room's roster who is **not present** on a given day is marked as remote for that day.

This mirrors exactly how the SharePoint files work: a blank seat that was filled on other days signals the person is working from home.

**Deduplication:** An employee may appear in multiple seat sub-blocks within the same room (Takoradi's continuation blocks). The deduplication step ensures that if an employee appears as present in *any* sub-block for a given day, they are not incorrectly marked remote.

## Output Files

All output files are written as UTF-8 CSV files.

---

### `rooms.csv`
One row per room/section across all offices.

| Column | Description |
|---|---|
| `room_id` | UUID generated at runtime. Unique identifier for the room. |
| `office` | Office name (e.g. `Kumasi Office`) |
| `city` | City the office is in |
| `room_name` | Name of the room or section as found in the source file |
| `total_seats` | Total seat count declared in the source file (Kumasi only; `null` for others) |
| `floor_leads` | Semicolon-separated list of floor lead names (Kumasi only) |
| `block` | Block label — `A` or `B` (Accra only) |
| `floor_number` | Floor number extracted from the room name (Accra only) |

**Row count:** 17 (6 Kumasi + 5 Takoradi + 6 Accra)

---

### `seat_assignments.csv`
One row per seat per day. This is the most granular table — it records exactly who sat where on each day.

| Column | Description |
|---|---|
| `room_id` | Foreign key to `rooms.csv` |
| `room_name` | Room name (denormalised for readability) |
| `office` | Office name |
| `day` | Day of week (Monday – Friday) |
| `seat` | Seat label (e.g. `Seat 1`, `Seat 12`) |
| `employee` | Name of the employee occupying the seat. `null` if the seat was empty. |
| `is_occupied` | `True` if an employee was assigned; `False` if the seat was empty |
| `is_hot_desk` | `True` if the seat is a bookable hot desk (Accra only); `False` otherwise |

**Row count:** 1,930

---

### `occupancy.csv`
Same structure as `seat_assignments.csv` with the addition of the reported vacancy count. This table is focused on the occupancy state of each seat and is intended for aggregation and reporting.

| Column | Description |
|---|---|
| `room_id` | Foreign key to `rooms.csv` |
| `room_name` | Room name |
| `office` | Office name |
| `day` | Day of week |
| `seat` | Seat label |
| `employee` | Name of the occupying employee (`null` if empty) |
| `is_occupied` | `True` if occupied |
| `vacant_count_reported` | The number of vacant seats for that day as stated in the source file. Only available for Kumasi and Takoradi; `null` for Accra. |
| `is_hot_desk` | `True` for bookable hot-desk seats (Accra only) |

**Row count:** 1,930

---

### `remote_log.csv`
One row per employee per room per day, covering both remote and in-office records. This is the full picture — useful for auditing or building dashboards that show overall presence rates.

| Column | Description |
|---|---|
| `employee` | Employee full name |
| `office` | Office name |
| `room_name` | Room the employee is assigned to |
| `day` | Day of week |
| `is_remote` | `True` if the employee was remote that day; `False` if they were in office |

**Row count:** 1,790

---

### `remote_true.csv`
A filtered subset of `remote_log.csv` containing **only** employees who were confirmed remote on a given day (`is_remote = True`). The `is_remote` column is dropped since every row represents a remote day by definition.

| Column | Description |
|---|---|
| `employee` | Employee full name |
| `office` | Office name |
| `room_name` | Room the employee is assigned to |
| `day` | Day of week they were remote |

Sorted by: `office` → `room_name` → `day` → `employee`

**Row count:** 536

## Key Design Decisions

**No hardcoded column numbers.** Each parser discovers seat columns dynamically by scanning for labels that start with `Seat`. This means the script continues to work correctly if columns are added or reordered in future SharePoint exports.

**Roster-based remote inference.** The remote status is computed from the union of all names seen across all five days for a given room. This avoids needing a separate master employee list as an input.

**Present wins over remote during deduplication.** When merging sub-blocks in Takoradi, if an employee appears in two different sub-blocks and one marks them present while the other would mark them remote (due to a blank in that sub-block), presence always wins. This prevents false remote flags.

**Hot-desk seats are excluded from the remote roster.** The `Book before Use` marker in the Accra file indicates seats available for ad-hoc booking. These are never treated as employee names and are excluded from the remote detection roster entirely.

**UUIDs are generated fresh on each run.** The `room_id` values in `rooms.csv` are new UUIDs every time the script runs. If you are loading these into a database incrementally, you should either use the `room_name + office` combination as the natural key for lookups, or generate stable IDs upstream before loading.

## Extending to New Offices

To add a new office or country:

1. Inspect the new SharePoint CSV and identify the delimiter, how room headers are structured, and where seat labels and day rows appear.
2. Write a new `parse_<officename>(path)` function following the same pattern as the existing three — it should return a dict with keys `rooms`, `assignments`, `occupancy`, and `remote`.
3. Call the new function in `main()` and include its result in the `merge_results(...)` call.
4. Add the new office to the `OFFICES` config dictionary at the top of the script.

## Known Limitations

- The script processes a **single week snapshot** per run. The source SharePoint files do not contain date ranges — they represent the current week's arrangement. To build a historical record, run the script weekly and append outputs to a persistent store with a `week_of` date column.
- **Kweikuma** in the Kumasi file appears to have all seats empty across all days in the current export. The script handles this gracefully (producing rows with `is_occupied = False`) but it may indicate the room is currently unused or the data was not filled in.
- Employee names are taken as-is from the source files. Minor spelling variations of the same person's name across different weeks or offices will appear as separate employees. A name normalisation or entity resolution step would be needed before joining this data against an HR system.
